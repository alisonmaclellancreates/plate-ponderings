# Step 42: real accounts, handles and header

## Domain and state transitions

- Keep the existing `profiles` and separate `user_roles`. Signup creates an auth account and its generated profile atomically, without AI. Signin hydrates the caller's handle and verified roles; signout clears the session and analytics identity.
- Handle editing follows `format/reserved check → availability check → save attempt → repeat checks → AI safety check → atomic update`. Rejection, AI failure or a concurrent collision leaves the existing handle unchanged. No pending handles.
- Preserve the existing page layouts, brand artwork and copy. Plate, story, submissions and settings data remain previews unless required for this account flow. No new contribution, notification, demo or admin-management features.

## Database changes requiring approval

1. **Generated handles on signup.** Add a fixed-search-path `SECURITY DEFINER` function in `public`, invoked by an app-owned `AFTER INSERT` trigger on `auth.users`. Ignore user-supplied handle/role metadata. Insert `Traveler` plus exactly four digits into `profiles`; always exclude `Traveler4821`, reserved for the demo account created in Step 52. On a case-insensitive unique collision, try another unused number. Exhaustion fails account creation cleanly rather than creating an account without a profile. The generator has 9,999 possible handles, which is a deliberate V0 capacity boundary.
2. **Handle validation.** Keep the existing unique index on `lower(handle)`. Add an immutable format/reserved-name constraint: 3–20 ASCII letters, digits or underscores, excluding the brief's complete reserved list, ignoring case. Validate existing rows before applying and verify the constraint afterward. Current database check found zero profiles, missing profiles, malformed handles, reserved handles or duplicate handles. Include a backfill for any account missing a profile if one appears before application, using the same generator without AI.
3. **Durable rate limiting.** Add `public.handle_save_attempts` with `id uuid`, `user_id uuid`, `attempted_at timestamptz default now()` and an index on `(user_id, attempted_at)`. No foreign key to `auth.users`. Revoke all from `anon` and `authenticated`, grant only `service_role`, enable RLS with no browser policies. A service-only, fixed-search-path function serializes requests per user and records an attempt only below the limit. **Approved: at most five handle-save attempts per person in any rolling 15 minutes**, including rejected attempts; availability checks do not consume attempts. Demo callers are refused before recording attempts or invoking AI.
4. **Privileges.** Keep `profiles` and `user_roles` owner-only SELECT policies and authenticated SELECT grants, because authenticated server functions use the verified caller's RLS client to read their own account. Do not add browser INSERT/UPDATE/DELETE grants or profile-write policies. Elevated profile updates happen only inside a verified server function, to its caller's own id, after demo, validation, rate and AI checks. Revoke default PUBLIC/anon/authenticated execution on new privileged helpers and grant execution only to `service_role`. Existing Step 41 grants and policies otherwise remain unchanged.

No `ai_access_state` table. AI failures leave the old handle unchanged and show the brief's exact handle-check-unavailable message. Log provider denials and credit blocks server-side using safe status/category and gateway-issued correlation ids only, never handles, prompts, credentials or raw responses. Ordinary unavailability can be retried by a fresh save within the approved rate limit. **Unresolved requested exception:** removing every record that stops future calls is incompatible with the AI Gateway's mandatory terminal-error handling. Explicit provider access denials require persisted blocking until access is restored; credit blocks require paused automated work and explicit recovery. Required bookkeeping remains limited to service-only save outcome records, not a separate pause table. A rate limit does not replace these rules, and zero cost for denied requests is not assumed. A moderation refusal ends only that save.

No migration or auth-setting change will be applied before approval.
